# DP-300 Notes: Cell-Level Encryption (CLE) in Azure SQL Database

Object-level encryption, built from this lab:
[terraform/main.tf](terraform/main.tf) and [terraform/modules/](terraform/modules/) → [export_import_cert_for_cle.sql](sql/export_import_cert_for_cle.sql)
(with [always-encrypted.ps1](always-encrypted.ps1) for contrast)

---

## 1. One-minute summary

| Question | Answer |
|---|---|
| What is CLE? | Encrypting **individual columns or values** with T-SQL functions (`ENCRYPTBYKEY` / `DECRYPTBYKEY`) using keys stored **inside the database**. |
| Who does the crypto? | **SQL Server (the engine)**. Not the client. |
| Data type of an encrypted column | `varbinary` (max 8,000 bytes of output) |
| App changes needed? | **Yes**. Every INSERT, UPDATE and SELECT must call the functions and open the key. |
| Does it stop DBAs? | **No**. Anyone with enough database permission (dbo, server admin) can decrypt. Use **Always Encrypted** for that. |
| Typical exam keywords | "specific column", "T-SQL", "symmetric key", "certificate", "database master key", "ENCRYPTBYKEY" |

## 2. The key hierarchy (what this lab built)

```
Service Master Key (SMK)            Managed by Azure. You never touch it.
        │ protects
        ▼
Database Master Key (DMK)           B1: CREATE MASTER KEY ... BY PASSWORD
        │ protects                  (password generated by Terraform and stored
        ▼                           in Key Vault as secret "sql-dmk-password")
Certificate  CLE_Cert               A1–A7 + B2: generated in Key Vault (sql-lab-cert),
        │ protects                  exported, converted to PVK, imported FROM BINARY.
        ▼                           Its private key is then ENCRYPTED_BY_MASTER_KEY.
Symmetric key  CLE_Key (AES_256)    B4: CREATE SYMMETRIC KEY ... BY CERTIFICATE
        │ encrypts
        ▼
Purchasing.Suppliers.BankAccountNumberEnc   (varbinary(256))   B5–B6
```

**Why this chain?**
- **Symmetric keys** (AES) are fast. They do the bulk work on the data.
- **Certificates and asymmetric keys** (RSA) are slow but good at protecting other keys.
- The **DMK** protects the certificate's private key. Because the DMK is itself protected by the service master key, the engine can open the certificate **without a password**. That is why B6 needs no password.

**Exam fact:** each level protects the one below it. Lose a level (for example, drop the certificate) and everything below it can no longer be decrypted.

## 3. Walkthrough of this lab (what each step proves)

### Part A: get the certificate from Key Vault into SQL (bash)

| Step | What happens | Why it matters for the exam |
|---|---|---|
| A2 | Download `sql-lab-cert` as a PFX from Key Vault | Key Vault is the **source of truth and the backup** for the certificate |
| A3 / A4 | Split it into a public cert (DER) and a private key (PEM) | SQL needs the two parts separately |
| A6 | Convert the private key to **PVK**, protected by a one-time password | `CREATE CERTIFICATE ... WITH PRIVATE KEY` accepts PVK, not PEM |
| A7 | Generate `CREATE CERTIFICATE ... FROM BINARY` | **Azure SQL Database has no file system access**, so `FROM FILE` and `BACKUP CERTIFICATE TO FILE` don't work. Use `FROM BINARY`. |

### Part B: build CLE in the database (T-SQL)

```sql
-- B1  DMK
CREATE MASTER KEY ENCRYPTION BY PASSWORD = '<sql-dmk-password>';

-- B2  Import the certificate (CREATE CERTIFICATE CLE_Cert FROM BINARY ...)

-- B3  Verify
SELECT name, thumbprint, pvt_key_encryption_type_desc, expiry_date
FROM sys.certificates WHERE name = 'CLE_Cert';
--  pvt_key_encryption_type_desc = ENCRYPTED_BY_MASTER_KEY  → no password needed to use it
--  thumbprint matches Key Vault                            → it is the same certificate

-- B4  Data key
CREATE SYMMETRIC KEY CLE_Key WITH ALGORITHM = AES_256
ENCRYPTION BY CERTIFICATE CLE_Cert;

-- B5  Encrypted column (always varbinary)
ALTER TABLE Purchasing.Suppliers ADD BankAccountNumberEnc varbinary(256) NULL;

-- B6  Encrypt
OPEN SYMMETRIC KEY CLE_Key DECRYPTION BY CERTIFICATE CLE_Cert;
UPDATE Purchasing.Suppliers
   SET BankAccountNumberEnc = ENCRYPTBYKEY(KEY_GUID('CLE_Key'), BankAccountNumber)
 WHERE BankAccountNumber IS NOT NULL;
CLOSE SYMMETRIC KEY CLE_Key;

-- B7  Decrypt
OPEN SYMMETRIC KEY CLE_Key DECRYPTION BY CERTIFICATE CLE_Cert;
SELECT CONVERT(nvarchar(20), DECRYPTBYKEY(BankAccountNumberEnc)) AS decrypted
FROM Purchasing.Suppliers;
CLOSE SYMMETRIC KEY CLE_Key;
```

### Function cheat sheet

| Function | Needs `OPEN SYMMETRIC KEY` first? | Notes |
|---|---|---|
| `ENCRYPTBYKEY(KEY_GUID('k'), value [, add_authenticator, authenticator])` | **Yes** | Returns **NULL silently** if the key is not open |
| `DECRYPTBYKEY(cipher [, add_authenticator, authenticator])` | **Yes** | No key name needed: the ciphertext carries the key GUID. Returns NULL if it can't decrypt. |
| `DECRYPTBYKEYAUTOCERT(CERT_ID('c'), NULL, cipher)` | **No** (opens and closes the key for you) | Handy in views and procedures |
| `ENCRYPTBYCERT` / `DECRYPTBYCERT` | n/a | RSA directly. Slow and size-limited, so use it only for small values. |
| `ENCRYPTBYPASSPHRASE` / `DECRYPTBYPASSPHRASE` | n/a | No key objects at all. The passphrase lives in your code, so it's weak. |

## 4. Logins, users and roles in Azure SQL Database

### Who exists in this lab

| Identity | Created by | Where | Effective rights |
|---|---|---|---|
| `sqladminuser` (SQL authentication) | Terraform `administrator_login` | Server (master) | **Server admin**: maps to **dbo** in every database |
| Entra admin (`labuser_...`) | Terraform `azuread_administrator` | Server | Also **dbo** in every database, and can create Entra users |
| A non-admin user | You (section 6) | One database | Only what you GRANT |

### Creating identities (learn all three for the exam)

```sql
-- 1. Server login + database user (login lives in master)
--    run in master:
CREATE LOGIN cle_app WITH PASSWORD = 'Str0ng!Passw0rd#';
--    run in the user database:
CREATE USER cle_app FROM LOGIN cle_app;

-- 2. Contained database user (no login; authenticates to the database directly)
CREATE USER cle_contained WITH PASSWORD = 'Str0ng!Passw0rd#';

-- 3. Microsoft Entra ID user or group (run while connected as an Entra identity)
CREATE USER [someone@contoso.com] FROM EXTERNAL PROVIDER;
```

### Server-level roles in Azure SQL Database

Azure SQL Database has **no `sysadmin`**. It has fixed server roles named `##MS_...##`, managed from master:

| Role | Grants | Can it decrypt CLE data? |
|---|---|---|
| `##MS_DatabaseManager##` | Create and delete databases (becomes dbo of databases it creates) | Only in databases where it is dbo |
| `##MS_LoginManager##` | Create and delete logins | No |
| `##MS_DatabaseConnector##` | CONNECT to any database | No |
| `##MS_DefinitionReader##` | VIEW ANY DEFINITION | **No**. It can *see* that `CLE_Key` and `CLE_Cert` exist, but it can't open them (no CONTROL on the certificate). |
| `##MS_SecurityDefinitionReader##` | View security catalog views | No (metadata only) |
| `##MS_ServerStateReader##` / `##MS_ServerStateManager##` | DMVs and server state | No |

```sql
-- in master
ALTER SERVER ROLE ##MS_DefinitionReader## ADD MEMBER cle_app;
```

**Exam fact:** no fixed server role gives access to encrypted data. Decryption needs **database-level** permissions on the key and certificate, or being dbo.

On-premises SQL Server and SQL Managed Instance do have `sysadmin`. It holds CONTROL SERVER, so it can always decrypt CLE data protected by the DMK.

## 5. Permissions needed, operation by operation

| Operation | Minimum permission | dbo / server admin |
|---|---|---|
| `CREATE MASTER KEY` | **CONTROL** on the database | ✅ |
| `CREATE CERTIFICATE` | **CREATE CERTIFICATE** on the database | ✅ |
| `CREATE SYMMETRIC KEY ... BY CERTIFICATE` | **ALTER ANY SYMMETRIC KEY** on the database, plus **VIEW DEFINITION** on the certificate | ✅ |
| `OPEN SYMMETRIC KEY ... DECRYPTION BY CERTIFICATE` | **Any permission on the key** (usually VIEW DEFINITION), not denied VIEW DEFINITION, plus **CONTROL on the certificate** (plus the certificate password if the private key is password-protected rather than DMK-protected) | ✅ |
| `ENCRYPTBYKEY` in an UPDATE | Key open (as above) + **UPDATE** on the table | ✅ |
| `DECRYPTBYKEY` in a SELECT | Key open (as above) + **SELECT** on the table | ✅ |
| `DECRYPTBYKEYAUTOCERT` | **VIEW DEFINITION** on the key + **CONTROL** on the certificate + SELECT | ✅ |
| See key and certificate metadata (`sys.symmetric_keys`, `sys.certificates`) | VIEW DEFINITION | ✅ |

The two grants to memorise:

```sql
GRANT VIEW DEFINITION ON SYMMETRIC KEY::CLE_Key  TO cle_app;
GRANT CONTROL         ON CERTIFICATE::CLE_Cert   TO cle_app;
```

## 6. Admin vs non-admin user: scenarios

### Advantages and trade-offs

| | Admin (server admin / Entra admin / db_owner) | Non-admin (granular grants) |
|---|---|---|
| Set up the hierarchy (DMK, certificate, key) | ✅ Can do everything in one session | ❌ Needs CONTROL on the database, CREATE CERTIFICATE and ALTER ANY SYMMETRIC KEY. That is effectively an admin job. |
| Encrypt and decrypt | ✅ Always, no extra grants | ✅ Only after the two grants above |
| Troubleshooting | Easy: nothing is "permission denied" | Errors look like "the key doesn't exist" (see below) |
| Least privilege / compliance | ❌ Can read *every* encrypted column. Too much power for an app. | ✅ Access limited to specific keys. Best practice for apps and analysts. |
| Separation of duties | ❌ None | Partial. The DBA can still decrypt, so true separation needs Always Encrypted. |
| Auditability | Hard to tell "admin did maintenance" from "admin read secrets" | Clear: only named principals can open the key |

**Rule of thumb:** use admin accounts to **build and maintain** the key hierarchy. Use non-admin accounts with **targeted grants** (or a stored procedure) to **use** it.

### Scenario 1: non-admin with SELECT only

```sql
-- as admin
CREATE USER cle_reader WITH PASSWORD = 'Str0ng!Passw0rd#';
GRANT SELECT ON Purchasing.Suppliers TO cle_reader;

-- as cle_reader
OPEN SYMMETRIC KEY CLE_Key DECRYPTION BY CERTIFICATE CLE_Cert;
-- ❌ Msg 15151: Cannot find the symmetric key 'CLE_Key', because it does not
--    exist or you do not have permission.

SELECT CONVERT(nvarchar(20), DECRYPTBYKEY(BankAccountNumberEnc))
FROM Purchasing.Suppliers;
-- ⚠️ No error. Every row returns NULL (the key isn't open).
```

**Lesson:** the user can read the ciphertext but never the plaintext. Note the error message hides whether the key exists at all.

### Scenario 2: grant key access to the non-admin

```sql
-- as admin
GRANT VIEW DEFINITION ON SYMMETRIC KEY::CLE_Key TO cle_reader;
GRANT CONTROL         ON CERTIFICATE::CLE_Cert  TO cle_reader;
-- as cle_reader: OPEN SYMMETRIC KEY ... and DECRYPTBYKEY now work ✅
```

### Scenario 3: decrypt without giving the user any key permissions (best practice for apps)

```sql
CREATE OR ALTER PROCEDURE Purchasing.GetSupplierBankAccount @SupplierID int
WITH EXECUTE AS OWNER          -- runs with dbo's rights
AS
BEGIN
    OPEN SYMMETRIC KEY CLE_Key DECRYPTION BY CERTIFICATE CLE_Cert;
    SELECT SupplierID,
           CONVERT(nvarchar(20), DECRYPTBYKEY(BankAccountNumberEnc)) AS BankAccountNumber
    FROM Purchasing.Suppliers WHERE SupplierID = @SupplierID;
    CLOSE SYMMETRIC KEY CLE_Key;
END;
GO
GRANT EXECUTE ON Purchasing.GetSupplierBankAccount TO cle_reader;
```

**Exam fact:** **ownership chaining does NOT cover key permissions.** A plain procedure owned by dbo still fails `OPEN SYMMETRIC KEY` for the caller. You need `EXECUTE AS` or **module signing** (sign the procedure with a certificate).

### Scenario 4: block a specific user

```sql
DENY VIEW DEFINITION ON SYMMETRIC KEY::CLE_Key TO cle_reader;
-- OPEN fails even if the user has other permissions on the key
```

### Scenario 5: the DBA problem

The compliance team says *"DBAs must not be able to read bank account numbers."*
→ **CLE can't satisfy this.** dbo has CONTROL over the key and certificate, and the DMK opens automatically.
→ Answer: **Always Encrypted** with the CMK in Key Vault (see [always-encrypted.ps1](always-encrypted.ps1)), giving the DBA no Key Vault access.

### Scenario 6: equality search on an encrypted column

`WHERE DECRYPTBYKEY(col) = '123'` decrypts every row and can't use an index.
→ Add a **hash column** (`HASHBYTES('SHA2_256', salt + value)`), index it, and search on the hash.

### Scenario 7: copy-paste attack

A user with UPDATE rights copies another row's ciphertext into their own row. It decrypts fine, because it's the same key.
→ Use the **authenticator** argument to bind each ciphertext to its row:

```sql
ENCRYPTBYKEY(KEY_GUID('CLE_Key'), BankAccountNumber, 1, CONVERT(varbinary(4), SupplierID))
DECRYPTBYKEY(BankAccountNumberEnc, 1, CONVERT(varbinary(4), SupplierID))
```

(This lab doesn't use an authenticator. It's a worthwhile improvement.)

## 7. Gotchas from this lab (high exam value)

1. **Convert back to the original data type.** `BankAccountNumber` is `nvarchar`, so B7 uses `CONVERT(nvarchar(20), ...)`. Converting to `varchar` returns garbage.
2. **`ENCRYPTBYKEY` returns NULL if the key isn't open.** Run B6's UPDATE without OPEN and you silently overwrite the column with NULLs.
3. **Keys stay open for the session** until `CLOSE SYMMETRIC KEY` (or `CLOSE ALL SYMMETRIC KEYS`). Check with `SELECT * FROM sys.openkeys;`.
4. **The plaintext column still exists after B6.** CLE only protects data once you drop `BankAccountNumber` (after checking that B7 matches).
5. **`varbinary` sizing.** Ciphertext is bigger than plaintext (header, IV and padding). `varbinary(256)` is plenty for `nvarchar(20)`.
6. **Recreating the symmetric key.** `CLE_Key` was created **without** `KEY_SOURCE` and `IDENTITY_VALUE`, so it can't be recreated identically. It survives only inside database backups and BACPACs. To use the same key in another database, create it with both options.
7. **Certificate expiry isn't enforced** for encryption. Key Vault auto-renewing `sql-lab-cert` doesn't change the copy in SQL, and that's fine.
8. **Azure SQL DB has no file access.** Use `FROM BINARY` (as in A7), not `FROM FILE` or `BACKUP CERTIFICATE ... TO FILE`.

## 8. CLE vs the other encryption features

| | TDE | **CLE** | Always Encrypted | Dynamic Data Masking |
|---|---|---|---|---|
| Scope | Whole database (files, backups, logs) | **Chosen columns or values** | Chosen columns | Chosen columns (display only) |
| Protects | Data at rest | At rest + in the database (ciphertext in tables) | At rest, in transit **and in use** | Nothing. It only hides values in query output. |
| Who encrypts | Engine | **Engine** | **Client driver** | n/a |
| App changes | None | **Yes (T-SQL functions)** | Connection string (`Column Encryption Setting=Enabled`) + parameterised queries | None |
| Stops DBAs? | No | **No** | **Yes** | No (`UNMASK` permission) |
| Keys | DEK protected by a TDE protector (this lab: an RSA key in Key Vault) | DMK → certificate → symmetric key, **in the database** | CEK in the database, CMK **outside** it (Key Vault) | n/a |
| In this lab | `azurerm_mssql_server_transparent_data_encryption` | `sql/export_import_cert_for_cle.sql` | `always-encrypted.ps1` | — |

## 10. Practice questions

1. **You must encrypt a single column with T-SQL so the database engine can decrypt it for authorised users. What do you create first?**
   A database master key. (The order: DMK → certificate → symmetric key → encrypt.)

2. **A user can SELECT from the table, but `DECRYPTBYKEY` returns NULL for every row. Why?**
   The symmetric key isn't open in their session, most likely because they lack VIEW DEFINITION on the key or CONTROL on the certificate.

3. **What's the minimum permission to `OPEN SYMMETRIC KEY CLE_Key DECRYPTION BY CERTIFICATE CLE_Cert`?**
   Any permission on the key (for example VIEW DEFINITION) plus CONTROL on the certificate.

4. **An app should read decrypted data but must never hold key permissions. What do you do?**
   Wrap the decryption in a stored procedure with `EXECUTE AS OWNER` (or sign it with a certificate) and grant EXECUTE only.

5. **Auditors require that the DBA team can't view the decrypted data. CLE or Always Encrypted?**
   Always Encrypted. CLE keys live in the database and dbo controls them.

6. **Which Azure SQL Database server role lets a user read CLE-encrypted data?**
   None. Server roles give metadata or management rights. Decryption needs database-level key permissions or dbo.

7. **Why does the lab use `CREATE CERTIFICATE ... FROM BINARY`?**
   Azure SQL Database can't read files, so the certificate and private key are passed as hex literals.

8. **You need the same symmetric key in two databases. What do you specify?**
   The same `KEY_SOURCE` and `IDENTITY_VALUE` (and algorithm) in both `CREATE SYMMETRIC KEY` statements.

9. **Which data type stores CLE output?**
   `varbinary`.

10. **How do you stop someone moving ciphertext between rows?**
    Use the authenticator parameters of `ENCRYPTBYKEY` / `DECRYPTBYKEY`, for example with the row's primary key.
